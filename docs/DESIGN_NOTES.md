## 1. Wire format

One header, `protocol/grad_proto.h`, defines the packet for every component.
All multi-byte fields are big-endian.

| Offset | Size | Field | Meaning |
|---|---|---|---|
| 0 | 4 | `job_id` | tenant / training job |
| 4 | 4 | `round` | training step |
| 8 | 4 | `chunk_id` | which slice of the gradient vector |
| 12 | 2 | `worker_id` | `0..num_workers-1` for a raw contribution; `0xFFFF` on packets an aggregator or the PS produces |
| 14 | 2 | `num_workers` | fan-in of the round (1..256) |
| 16 | 2 | `chunk_len` | int32 values that follow (1..64; 0 only on REGISTER) |
| 18 | 2 | `flags` | bits 15-12 version, bits 0-5 `NETSUM_F_*`, bits 6-11 reserved on v2, the exponent *e* on v3 |
| 20 | 4 x `chunk_len` | values | Q16.16 on v1/v2; `round(x * 2^e)` on v3 (§2) |
| 20 + 4 x `chunk_len` | 32 | contributor bitmap (v2 and v3) | bit *w* set iff worker *w* is included |

Version 0 is the legacy v1 format: `flags == 0` and no bitmap trailer. It is
still accepted as a raw contribution, so old senders and the current kernel
path keep working.

Version 3 is v2 plus a per-chunk exponent *e* (0-63) in flags bits 6-11
(§2). Everything else, including the trailer and every flag, is v2's; the
code gates the trailer, RESEND and FALLBACK on "has a trailer" (v2 or v3),
not on version 2. A v2 packet is treated as exponent 16.

| Flag | Bit | Set by | Meaning |
|---|---|---|---|
| `RESEND` | 0 | worker | retransmitted contribution (ATP's resend bit) |
| `ACK` | 1 | PS | result packet; carries the aggregated values |
| `OVERFLOW` | 2 | aggregator / PS; a v3 worker | the accumulation overflowed, or (v3 raw contribution) the worker's own value saturated; values are not trustworthy |
| `FALLBACK` | 3 | aggregator | raw contribution forwarded un-aggregated (best-effort fallback) |
| `PARTIAL` | 4 | aggregator | incomplete aggregate flushed on resend or TTL |
| `REGISTER` | 5 | worker | registration with the PS (job, worker id, fan-in) |

**Why every v2 packet carries the bitmap.** A raw contribution sets only its
own bit. An aggregator turns the completing raw packet into the aggregate *in
place* by overwriting values, `worker_id`, flags and bitmap, so a packet never
has to grow (`bpf_xdp_adjust_tail` is avoided entirely). The PS can always
check an incoming aggregate's contributors against what it already holds, even
for complete aggregates, which keeps the fallback merge safe (§Fallback). The
cost is 32 bytes per packet. The plan allowed growing the packet with
`bpf_xdp_adjust_tail` instead; the reserved trailer was chosen up front
because it needs no headroom or tailroom from the attach mode, which matters
in `xdpgeneric`, and because it makes every packet kind the same shape.

## 2. Fixed point

Values are Q16.16 in an `int32_t`. Workers convert with `netsum_to_fixed()`:
round half away from zero, saturate at the int32 limits, NaN to 0. The BPF verifier forbids floating point,
and integer addition is exact and order-independent, so every path (noagg,
userspace aggregation, XDP) produces bit-identical sums for the same inputs.
Accumulation uses `netsum_add_i32()`, an unsigned add that reports signed
overflow as `((a ^ r) & (b ^ r)) >> 31`; it has no C undefined behaviour and
compiles to a few ALU instructions in BPF. Overflow sets a sticky per-slot
flag; the round still completes, but it is reported as `[overflow]` (and the
forwarded aggregate carries `OVERFLOW`) instead of a sum.

**Per-chunk exponent (wire v3).** Q16.16 has a fixed resolution of 2^-16, so
gradients below about 1e-5 round to zero (`docs/RESULTS.md` §Quantization).
A v3 packet carries values as `round(x * 2^e)` with the chunk's exponent *e*
(0-63) in the header; `netsum_to_scaled()` converts (exact powers of two, no
libm), and the aggregators only add integers, so nothing on the data path
changes except bookkeeping:

* every slot records the exponent and version of its first contribution;
  a contribution at another exponent is dropped and counted
  (`scale_mismatch`), like a fan-in or length disagreement (§3);
* aggregates, PARTIAL flushes (forward tail and the TTL sweeper), results
  and ACKs are emitted at the slot's version and exponent, so the sweeper,
  which has no incoming packet, still produces the right header (a slot a
  legacy v1 packet opened emits v2, never flags 0);
* a worker whose own value saturates at *e* sets `OVERFLOW` on its raw
  contribution instead of sending a clipped value; the slot's sticky flag
  picks it up, so the result is flagged rather than wrong. (A v2 raw
  contribution with `OVERFLOW` is still rejected.)

*Agreement without a message.* All workers must use the same *e* for a
chunk. Every worker receives the identical summed result each round, so the
next exponent is a function of that result: `examples/train_mlp/scale_rule.py`
computes, in integers only so that any reimplementation (another language,
another float library) gives the same answer at a boundary,
`e' = e + (30 - 4 - bitlen(max |sum|))`, clamped to 0-63: the previous sum
lands near 2^26, leaving 4 bits (16x) of growth before overflow. An all-zero
sum raises *e* by 8 (otherwise underflow would be permanent); an `OVERFLOW`
result lowers it by 8. The rule needs every worker to have round *r-1*'s
result before it quantizes round *r*, i.e. synchronous rounds; the pipelined
C worker therefore takes a fixed exponent (`--frac-bits`). The rule is
offline-checked against an oracle that sees the current step's data
(`scripts/quant_study.py`, table in `docs/RESULTS.md`).

*Overflow is decided by the workers, and retried in the same step.* With N
workers each v3 value is bounded by `INT32_MAX / N` (`scale_rule.worker_limit`),
so no order of adding N values can overflow an int32 accumulator, and the
aggregators' own overflow check cannot fire on such traffic. A chunk
overflows exactly when some worker saturates (a sum that grew more than 16x,
or one worker's value large while the sum is small, +1 and -0.9999); that
worker marks its contribution `OVERFLOW`, the result comes back flagged, and
every worker, having computed the same thing, retries the chunk in the same
step at `e - 8` under the key `chunk_id | attempt << 24`. A fresh key means no
slot, tombstone, fallback entry or stored result of the failed attempt can
match the retry; the failed attempt's slots retire by ACK like any other. Up
to 9 attempts reach exponent 0; overflow there stops the job. Because the
decision depends only on each worker's own values, the local reference
(`adapt`) makes exactly the same retries, and the network path must match it
bit for bit at every attempt. The C reliable worker (`--frac-bits E`)
starts every chunk at the fixed exponent E, bounds its values the same way,
and retries the same way: on an `OVERFLOW` result it re-sends that chunk at
`e - 8` under the next attempt's key, ignores any late result of an earlier
attempt, and verifies a `--fixed` sum at the exponent that succeeded.

## 3. Admission and validation

`protocol/grad_parse.h` is the single definition of a valid packet; agg,
paramserver, the fuzzer and the XDP program call `netsum_parse()`. Checks run
in this order and the first failure is the verdict:

1. at least 20 bytes (`REJ_SHORT_HDR`);
2. version nibble 0, 2 or 3 (`REJ_VERSION`);
3. v1 has `flags == 0`; v2 has no reserved bit; on v3 bits 6-11 are the exponent (`REJ_RESERVED_FLAGS`);
4. `1 <= num_workers <= 256` (`REJ_NUM_WORKERS`);
5. `worker_id 0xFFFF` only on v2 (`REJ_WORKER_ID`);
6. kind and flag combination: REGISTER alone and from a worker; ACK alone
   and from `0xFFFF`; `0xFFFF` without RESEND/FALLBACK (AGGREGATE, or PARTIAL
   if flagged); a raw contribution without PARTIAL, without OVERFLOW unless
   v3, and with `worker_id < num_workers` (`REJ_FLAG_COMBO`, `REJ_WORKER_ID`);
7. `chunk_len <= 64` (`REJ_CHUNK_LEN_MAX`) and `> 0` except REGISTER (`REJ_CHUNK_LEN_ZERO`);
8. the datagram holds `chunk_len` values plus, on v2 and v3, the 32-byte bitmap (`REJ_TRUNCATED`).

Stateful rules, identical in agg, paramserver and the kernel:

* **The first accepted contribution fixes the round's fan-in and chunk
  length.** Later contributions that disagree are rejected and counted
  (`num_workers_mismatch`, `chunk_len_mismatch`); the slot is untouched.
  The same holds for the exponent on v3 (`scale_mismatch`; a v2 packet
  counts as exponent 16).
* A worker already in the slot's bitmap is a `duplicate` (`resend_duplicate`
  if RESEND is set).
* A contribution for a round that already completed is absorbed by the
  tombstone and counted as `late_duplicate` (bug C1).
* A malicious first packet claiming fan-in 1 can still complete a round with
  a single contribution. That is accepted; see §Threat model.

## 4. Threat model

NetSum defends against malformed packets (every length and range is checked
before use, fuzzed against a reference parser), misconfiguration (fan-in and
chunk-length disagreement, worker ids beyond the fan-in), crashed workers
(TTL reclamation), and loss, duplication and reordering on the network. It
does **not** defend against spoofed or malicious workers on the same L2
segment: there is no authentication, so a sender can forge any worker id or
claim a smaller fan-in. A control-plane-registered fan-in would close the
fan-in hole for registered jobs.

## 5. Concurrency

The kernel program runs concurrently on every CPU that receives packets.

* **Slots** live in a `BPF_MAP_TYPE_HASH` whose value embeds a
  `bpf_spin_lock`. Every read-modify-write of a slot (admission checks,
  accumulation, completion, writing the result into the packet) happens under
  that lock. No helper is called while it is held (the verifier forbids it),
  so the clock is read and counters are bumped outside the lock.
* **Slot creation** races are resolved by `bpf_map_update_elem(BPF_NOEXIST)`:
  exactly one CPU creates the slot; the losers re-look it up and join it.
* **Job quota** (bug C8): a slot is charged to its job *before* it is
  created. `__sync_fetch_and_add` returns the previous count (a `BPF_FETCH`
  atomic, compiled with `-mcpu=v3`), so concurrent CPUs cannot all pass the
  limit; a CPU that ends up over the limit, or loses the creation race, gives
  the unit back. Release is a saturating compare-and-swap loop (at most four
  attempts), so two concurrent releases can never wrap the counter to
  `0xFFFFFFFF`. The slot records whether it was charged (`charged`), so a
  slot created while no quota was configured is never released against one.
* When a job's count returns to zero its `job_quota_map` entry is deleted, so
  256 distinct job ids cannot fill the map for good (C7). A CPU that charged
  an entry at the same moment another CPU deleted it loses that unit; the
  quota then under-counts by one until the job's next slot. That is accepted
  and documented rather than taking a second lock.
* **Lock ordering:** slot locks and job state are never held together. The
  verifier allows only one held spin lock anyway.

## 6. Verifier constraints

Measured with `bpftool prog load` in the XDP load-test workflow (`-mcpu=v3`):

| Version | Kernel | Stack depth | Instructions processed | Run |
|---|---|---|---|---|
| v1 (base `f7ea415`) | 6.17 x86_64 | 352 bytes | 110,791 | 38114728912 |
| v2 before array mode (`96548ae`) | 7.0.0-1017-azure x86_64 | 200 bytes | 158,454 | 43758934811 |
| v2 with array mode (`38ec27d`) | CI runner x86_64 | 208 bytes | 335,067 | 43784550947 |
| v3 per-chunk exponent (`8212e91`) | CI runner x86_64 | 224 bytes | 422,645 | 43816639927 |

Adding array mode roughly doubled the instructions the verifier processes:
the hash-map and array paths reach the shared slot-update code with pointers
to different maps, so the verifier explores them separately. The sweep
program processes about 5,000-6,700 instructions (stack 40 bytes).

Packet size (`-DNETSUM_MAX_CHUNK_LEN=N`, `netsum-ctl verify` in `bpf-unit.yml`,
CI run 43784550947, x86_64; the local 7.0.11 aarch64 kernel gives 332,972 /
671,690 / rejected):

| values per packet | aggregator insns processed | sweep program | result |
|---|---|---|---|
| 64 (default) | 335,067 | 5,132 | accepted |
| 128 | 663,811 | 7,713 | accepted |
| 256 | > 1,000,000 | - | rejected: verifier complexity limit |

With the v3 exponent check (`8212e91`, run 43816639927): 64 values 422,645
(sweep 6,748), 128 values 840,360 (sweep 7,799), 256 rejected. The extra
outcome and the per-slot version/exponent bookkeeping cost about 26% at 64
values and take 128 to 84% of the 1,000,000 limit.

The default stays 64: 128 fits but leaves little room for future features,
and larger packets would need `bpf_loop()` or splitting the lane loops into
fixed sub-blocks. At 256, LLVM also rewrote the array-claim zeroing loop into
a `memset()` call, which BPF cannot make; an empty `asm volatile` barrier in
the loop body prevents it.

* The 300-byte `struct grad_slot fresh = {0}` stack local is gone: new slots
  are initialised from a zeroed per-CPU template map (`slot_template`). A
  per-CPU map may not contain a `bpf_spin_lock`, so the template uses a twin
  struct with a plain `uint32_t` in the lock's place; the kernel's value copy
  skips the lock field anyway.
* The accumulate loop is bounded by `NETSUM_MAX_CHUNK_LEN` and re-checks the
  packet bound on every iteration, so the verifier can prove each access.
  Accumulation and the write-back of the result into the packet are one loop:
  whether this contribution completes the slot is known before the loop.
* `chunk_len` from the parser is re-bounded locally before it is used in
  pointer arithmetic.
* `netsum_parse()` and `netsum_add_i32()` are forced inline: BPF does not
  allow a call while a spin lock is held.

## 7. Slot storage

Userspace (`common/slot_table.h`, shared by agg and paramserver): an
open-addressing table of `2^k` slots on the heap (`--slot-capacity-log2`,
default 16), FNV-1a over `(job_id, round, chunk_id)`, linear probing.
Deletion is **backward-shift** (Knuth vol. 3, Algorithm R): after removing a
slot, later entries of the same cluster whose home bucket is not in the gap
are moved back, so no "deleted" markers exist and every probe chain stays
intact. The previous implementation marked the slot free and broke chains
(bug C6). One slot is always left empty so a failed lookup terminates.
`tests/unit/test_slot_table.c` checks 200,000 random operations against a
linear-scan reference, including a table filled to capacity.

Per-job state (agg): a 256-entry job table holds the number of ACCUMULATING
slots per job, which is what the optional `max_slots_per_job` quota limits.
An entry is freed as soon as the job has no ACCUMULATING slots; its counters
are printed as a `[job-retired]` line. When all 256 entries are in use, new
slots are refused (`drop_job_table_full`): the table **fails closed**, so
rotating job ids can no longer escape the quota (bug C7).

Array mode in userspace (`agg --array-slots-log2 N`) mirrors the kernel's
`agg_array`: a pool of `2^N` aggregators indexed by `netsum_slot_hash(key) &
mask` (the function the kernel uses), each tagged with its owner. An EMPTY
aggregator is claimed; one owned by another key sends the contribution to the
PS with FALLBACK and records the key in a fallback set, so the key's later
contributions follow it even after the aggregator is freed (no key is split
between the aggregator and the PS). The ACK frees the aggregator and clears
the key from the set; tombstones expire as in hash mode; the per-job quota
does not apply, as in the kernel; v1 contributions that would fall back are
dropped, since v1 has no FALLBACK flag. Tests: `tests/test_reliability.py`
(`test_array_mode_*`).

## 8. Reclamation

Slot life cycle: `EMPTY -> ACCUMULATING -> COMPLETED -> EMPTY`, plus
`ACCUMULATING -> FLUSHED -> EMPTY` for partial flushes.

* On completion a slot becomes a **tombstone** (`COMPLETED`) that keeps its
  sum, so late duplicates are recognised instead of opening a slot that can
  never complete, and so a resend after completion can re-emit the result.
  Tombstones are not charged to the job quota.
* Userspace retires tombstones after `--tombstone-ttl-ms` (agg default 2 s,
  paramserver 10 s) through a FIFO of `(key, completed_us)` entries; an entry
  only deletes the slot if it is still that same completion. If the FIFO is
  full, the oldest tombstone is retired early.
* ACCUMULATING slots idle longer than `slot_ttl_ms` (agg, optional) are
  dropped with a `[reaped]` line.

Full state x event table (kernel; userspace agg is identical except where
noted). Every cell is covered by a `bpf-unit` case or a userspace test.

| State \ event | new raw contribution | same worker again | same worker, RESEND | fan-in or chunk_len disagrees | ACK from PS | TTL expired (sweeper) | array: key differs from the slot's tag |
|---|---|---|---|---|---|---|---|
| EMPTY (no slot) | create ACCUMULATING (quota, job table, capacity checked; over quota: drop, or FALLBACK under the fallback policy) | - | treated as new (the original never arrived) | - | count `ack_unexpected`, drop | - | claim the aggregator |
| ACCUMULATING | add; on the last worker forward the aggregate, -> COMPLETED | count `duplicate`, drop | flush the partial to the PS, -> FLUSHED, release quota | count mismatch, drop | discard (PS finished the key), release quota, count `ack_unexpected` | flush as PARTIAL, -> FLUSHED (agg: `slot_ttl_ms` reaps instead) | FALLBACK to the PS, remember the key |
| COMPLETED | count `late_duplicate`, drop | count `late_duplicate`, drop | re-send the stored aggregate | count mismatch, drop | retire (delete / EMPTY) | retire | FALLBACK |
| FLUSHED | forward as FALLBACK | count `duplicate`, drop | forward as FALLBACK | count mismatch, drop | retire | retire | FALLBACK |

In the kernel, tombstones are retired by the PS's ACK (deleted in hash mode,
reset to EMPTY in array mode) or by the TTL sweeper (§12): an ACCUMULATING
slot idle past the TTL is flushed to the PS as a PARTIAL and becomes FLUSHED;
an expired COMPLETED or FLUSHED slot is retired. Retiring on ACK means a
plain duplicate arriving after the ACK opens a fresh slot, which the sweeper
reclaims; ATP's switch behaves the same way (it frees aggregators on the
parameter packet and reclaims stale ones by timestamp). The same holds for a
lone RESEND after a lost result: it re-opens the key with one contributor,
and if that worker then receives the result anyway (the PS re-sends it to
every registered worker when another worker recovers), no second RESEND
arrives to flush it, so only the sweeper reclaims the slot. Kernel
deployments therefore need the sweeper running for slot hygiene, not only
for crashed workers (Scenarios R and R2 assert this). The userspace aggregator
behaves the same in hash and array mode; its equivalent is the reaper
(`slot_ttl_ms`), which drops such a slot (the PS already holds the result).
`tests/test_reliability.py` runs it wherever a test asserts that no slot is
left: without it, the tiny-pool test left one or two re-opened aggregators in
2 of 12 runs on a slow (emulated) Linux host.

## 9. Reliability

NetSum follows ATP's end-host reliability design, adapted to one aggregator
per path:

* **Result path (ACK).** When the parameter server completes a
  `(job, round, chunk)` it sends one result packet (`ACK`, `worker_id 0xFFFF`,
  the sum and the contributor bitmap; `ACK|OVERFLOW` if the sum overflowed)
  first to the aggregator (`--ack-to`), which retires its slot, then to every
  worker it knows for that job. Workers make themselves known with an
  idempotent `REGISTER` packet sent at start-up and again with every
  retransmission, so a lost registration heals itself; a worker that sends
  directly to the PS (no aggregator) is also learned from its packets. ACKs
  for the aggregator go to its normal gradient port (9876) and are told apart
  by the `ACK` flag: one socket in `agg`, one port dispatch in XDP. ATP uses
  IGMP multicast for parameters; NetSum unicasts.
* **Worker (`worker --mode reliable`).** A gradient of `--vector-len` values
  per round is cut into chunks of up to 64 values. Up to `--window` chunks are
  in flight; a chunk without a result after its RTO (`--rto-ms`, default 50)
  is re-sent with `RESEND`, the RTO doubles up to 1 s, and after
  `--max-retries` (default 10) the worker exits with code 2. `--sync` waits
  for every result of round r before starting round r+1. In `--fixed` mode the
  worker checks every result lane against `workers x value`.
  `--drop-every K` and `--drop-result-every K` simulate the loss of every K-th
  first transmission and every K-th result.
* **Aggregator on RESEND** (agg and XDP):

| Slot state | RESEND contribution | Action |
|---|---|---|
| none | - | create and accept (the original never arrived) |
| ACCUMULATING | worker not yet in bitmap | accept (the original was lost) |
| ACCUMULATING | worker already in bitmap | **flush**: send the partial sum and bitmap to the PS as `PARTIAL`, mark the slot `FLUSHED`, release its quota unit |
| COMPLETED | any | re-send the stored aggregate (the aggregate or the result was lost) |
| FLUSHED | any (or a new worker) | forward the contribution itself as `FALLBACK`; the PS owns the key now |

* **Parameter server on a key it already completed:** a RESEND, a fallback,
  a partial or an aggregate means somebody is still waiting, almost always
  because a result was lost, so the PS re-sends the stored result (bug C13:
  before this, a worker whose result was lost could never finish). A plain
  duplicate without RESEND is only counted.
* **Retry horizon.** A worker gives up after about 50+100+200+400+800 ms +
  5 x 1 s ~= 6.5 s. The PS keeps completed keys for `--tombstone-ttl-ms`
  (default 10 s), longer than that, so any resend inside the horizon finds
  the result. The aggregator's tombstones only need to cover the time until
  the ACK; after an ACK, a late resend opens a fresh slot, its next resend
  flushes it as a partial, and the PS answers with the stored result. That
  costs one extra RTO in the rare lost-result case and keeps the aggregator's
  state small.

Measured on the userspace path (`tests/test_reliability.py`, 3 workers x 8
rounds x 1024 values, every 5th first transmission and every 7th result
dropped): every worker received all 128 results with correct sums; the
aggregator created 149 slots (21 re-opened by resends after a lost result),
flushed 16 partials, forwarded 42 fallbacks, and every slot was retired by an
ACK; the PS re-sent 21 results.

## 10. Fallback

Contributions for one key can reach the parameter server by several paths:
raw (no aggregator), FALLBACK (an aggregator forwarded a contribution it did
not aggregate), PARTIAL (an aggregator flushed an incomplete slot) and a
complete aggregate. Every one of them carries a contributor bitmap, so the PS
merges by sets and never counts a worker twice:

| Incoming set I vs held set H | Action |
|---|---|
| disjoint | add the sum, `H = H u I` |
| I is a subset of H | drop (`overlap_subset`): nothing new |
| H is a subset of I | replace H's sum with I's (`overlap_superset`) |
| any other overlap | reject (`overlap_rejected`); the remaining workers' resends finish the key |
| key already completed | count `aggregate_conflict` / `late_duplicate` and re-send the stored result |

The superset rule is what keeps loss recovery live. In Scenario J2 the
sweeper flushes `{0,1}` as a PARTIAL and later retires the FLUSHED slot;
when the workers retransmit, the aggregator re-creates the slot and completes
it with `{0,1,2}`. Without the rule the PS rejected that aggregate because it
overlapped the partial it held, the aggregator re-sent it on every RESEND,
and the round never completed (bug C14, found by J2 on the CI kernel).
Integer sums are exact, so replacing is always correct when the incoming
aggregate covers everything held. A partial overlap could be resolved by
subtracting per-worker values the PS kept; NetSum does not keep them, and the
remaining workers' resends, forwarded as fallbacks, complete the key anyway.

## 11. Observability

`protocol/netsum_stats.h` defines one counter enum used by every path. In the
kernel it indexes a `BPF_MAP_TYPE_PERCPU_ARRAY` incremented with a plain
`(*v)++` (no atomics, no cross-CPU cache traffic); readers sum across CPUs.
agg and paramserver keep the same counters in a plain array and print them as
one `[stats-all]` JSON line on SIGUSR1 and at exit. CI checks exact counter
deltas per scenario (`ci/check_stat.py`), not "greater than zero".

## 12. Control plane

`ctl/netsum_ctl.c` (`make ctl`, Linux) is the only tool that loads, attaches
and inspects the program; CI and the benchmarks use nothing else.

* `attach --ifname IF [--ifname IF2] --mode native|generic|auto` loads the
  object with libbpf, pins both programs and every map under `--pin`
  (default `/sys/fs/bpf/netsum`) and attaches with `bpf_xdp_attach`. It then
  reads the mode back with `bpf_xdp_query` and prints what the kernel chose,
  never what was asked for. A second `attach` reuses the pinned program, so
  one program and one set of maps can serve several interfaces.
* `config`, `stats` (per-CPU counters summed, plus `run_cnt` and
  `run_time_ns` when `kernel.bpf_stats_enabled` is on), `slots` (consistent
  snapshot with `BPF_F_LOCK`), `jobs`; `--json` on everything.
* `sweep --ttl-ms N --interval-ms M [--once | --duration-ms D]` is the TTL
  reclaimer. It snapshots the keys of `slot_map`, then runs the in-kernel
  `netsum_sweep` program once per key through `BPF_PROG_TEST_RUN`. Under the
  slot lock that program flushes an expired ACCUMULATING slot as a PARTIAL
  (returned as `XDP_TX`; the tool sends it to the PS) and marks it FLUSHED, or
  deletes an expired COMPLETED/FLUSHED slot (`XDP_DROP`). Doing the
  transition in the kernel means userspace never rewrites a slot, so a
  contribution or completion racing the sweeper is never lost, and the quota
  release uses the same atomic path as the data plane. ATP's switch checks
  aggregator timestamps in the data plane; a BPF program cannot run without a
  packet or timer, and this keeps the program free of `bpf_timer`.
* Struct layouts come from `protocol/netsum_maps.h`; there is no second copy.

## 13. Topology

**Correctness scenarios** (`xdp-loadtest.yml`): one veth pair. `veth0`
(10.200.1.1, root namespace) carries the XDP program; workers and the
parameter server share namespace `ns1` behind `veth1` (10.200.1.2).
Aggregates leave with `XDP_TX`, rewritten to the aggregator's own source
MAC/IP, so no `accept_local` relaxation is needed.

**Benchmark** (`scripts/topo.sh`): three namespaces.

```
 ns_w (workers)                root ns (aggregator)               ns_ps (parameter server)
 10.10.1.2  veth_w1 <------> veth_w0 10.10.1.1
                             veth_p0 10.10.2.1 <------> veth_p1 10.10.2.2
```

* The same XDP program and maps are attached to `veth_w0` (gradients from
  workers) and `veth_p0` (ACKs from the PS). Aggregates, partials and
  fallbacks are redirected out of `veth_p0` with `bpf_redirect`, addressed
  from `veth_p0` to `veth_p1`.
* Results from the PS to the workers, and all noagg traffic, are routed by
  the root namespace (`ip_forward=1`). Hosts running Docker (GitHub runners)
  set the iptables FORWARD policy to DROP, so `topo.sh` accepts exactly these
  two links.
* Native-mode XDP on veth delivers redirected frames to the peer only if the
  peer can receive them on its NAPI path; `topo.sh` enables GRO on
  `veth_p1` (kernel >= 5.13). Verified on 7.0.11 (local) and on the CI
  kernel 7.0.0-1016-aws, where `netsum-ctl attach --mode native` reported
  native and the PS received every aggregate.
* On veth, the receiver's processing (including XDP) runs on the sending
  CPU: per-CPU NET_RX softirq counts in the v2 benchmark are the same with
  and without XDP aggregation.

## 15. Benchmark methodology

**v2 (primary, `scripts/bench_v2.sh`, `bench.yml`).** Three-namespace
topology (§13). Configurations: noagg, userspace aggregation, XDP generic,
XDP native (only if the kernel reports native attach) and XDP array mode.
The load generator is the reliable worker, so every configuration returns
results to the workers and the measured time is end to end. Throughput:
4,000 rounds of 1,024 values (16 chunks), window 64, 8 trials per cell;
latency: 2,000 synchronous rounds, 5 trials per cell; 2, 4 and 8 workers.
Workers are pinned to CPUs 0-1, `agg` to 2, the PS to 3. Each trial starts
from freshly loaded maps and restarted processes. Recorded per trial: every
worker's result summary (any wrong or missing result fails the run), XDP
`run_time_ns / run_cnt`, `agg --profile` algorithm time per packet, on-CPU
time of agg and PS (`/proc/<pid>/schedstat`), NET_RX softirqs per CPU and
every counter. Accounting: every packet the XDP program saw must end in
exactly one outcome counter. Pre-registered tests (written in the log before
the run): per worker count, xdp-generic and xdp-native vs userspace on
throughput (family T) and per-trial median round time (family L);
permutation test on Cliff's delta, Holm within each family, ratio of medians
with bootstrap CIs. Fairness: three jobs of fan-in 2 with windows 64/32/16
run concurrently under no policy, a drop quota, a fallback quota and a
64-slot array; goodput is measured over the window in which all three jobs
are active; Jain's index over raw goodput and over goodput/demand.

**Benchmark-lite (history).**

**Benchmark-lite** (`scripts/bench_lite.sh`, workflow `bench-lite.yml`) is the
first measurement of the XDP path. It is deliberately small and runs on the
correctness topology:

* **Topology:** one host, two network namespaces joined by a veth pair. The
  aggregator side is the root namespace (`veth0`, 10.200.1.1, XDP attached in
  `xdpgeneric` mode); the parameter server runs in `ns1` (`veth1`, 10.200.1.2).
  * noagg: the sender (root ns) sends every contribution to the PS: one veth crossing.
  * useragg: the sender (ns1) sends to `agg` in the root ns, which forwards one aggregate per round to the PS.
  * xdp: the sender (ns1) sends to `veth0`; the XDP program consumes partial contributions and bounces each completed aggregate back with `XDP_TX`.
* **Load:** `bench/lite_sender.c`, one process, round-major order (all workers
  of round r, then r+1), single-chunk rounds of 16 values, paced open loop at
  100k / 200k / 400k packets/s or unpaced. Nothing waits for results; there is
  no result path yet.
* **Per trial:** 25,000 rounds; the PS and agg are restarted and the XDP
  program reloaded, so every trial starts from empty maps (kernel tombstones
  were not yet retired when it ran, and 25,000 stays below the 65,536-slot map).
* **Metrics:** completion ratio (rounds completed at the PS / rounds offered);
  goodput (completed rounds / time between first and last completion);
  sender rate achieved; XDP program cost `run_time_ns / run_cnt` from
  `kernel.bpf_stats_enabled`; on-CPU time of agg and PS from
  `/proc/<pid>/schedstat` divided by packets they received; UDP
  `RcvbufErrors` on both sides.
* **Accounting identity (checked per trial):** every packet sent is either
  received at the next hop or counted as a socket drop there, and every packet
  the XDP program sees ends in exactly one outcome counter. Loss is not an
  imbalance; it lowers the completion ratio.
* **Statistics:** medians with percentile-bootstrap 95% CIs over trials (the
  independent unit). Pre-registered tests, per worker count, useragg vs xdp
  with the sender unpaced: F1 goodput, F2 completion ratio; two-sided
  permutation test on Cliff's delta (2,000 relabelings, seed 1234), ratio of
  medians with a bootstrap CI, Holm-Bonferroni within each family. Paced
  cells are descriptive: in an open loop their goodput equals the offered rate.
* **Caveats:** GitHub-hosted runners are shared VMs; veth is a software
  device; generic XDP runs after the kernel has built an skb, so it skips the
  socket layer but not packet allocation; the sender, the aggregator and the
  PS share one host's CPUs and nothing is pinned. Numbers compare paths on the
  same machine in the same run; they are not line-rate claims.

## 16. Known issues

| ID | Bug | Status |
|---|---|---|
| C1 | late duplicate after completion re-creates a never-completing slot | fixed (tombstones) in userspace and kernel |
| C2 | `worker_id` not checked against the fan-in | fixed in the shared parser |
| C3 | fan-in taken from the first packet and never cross-checked | fixed in userspace and kernel |
| C4 | silent int32 wrap of the accumulator | fixed (`[overflow]`, `OVERFLOW` flag) in userspace and kernel |
| C5 | paramserver lacked agg's length and fan-in checks | fixed (shared parser) |
| C6 | slot free broke linear-probe chains | fixed (backward-shift deletion) |
| C7 | quota failed open after 256 job ids | fixed (free at zero, fail closed) in userspace and kernel |
| C8 | kernel quota check-then-act race, decrement underflow | fixed (reserve-before-create, saturating CAS) |
| C9 | forwarded aggregate keeps the worker's source MAC/IP | fixed (source rewritten from config); redirect to another interface supported |
| C10 | v1 benchmark measured serial process launches | replaced: benchmark-lite, then the closed-loop v2 benchmark |
| C11 | fuzzer tested copies of the checks | fixed: fuzzes `grad_parse.h`; bpf-unit replays the corpus through the loaded program |
| C12 | a test that could not fail; CI checks weaker than documented | fixed |
| C13 | a lost result could never be recovered: the PS ignored late packets for keys it had completed | fixed: the PS re-sends the stored result |
| C14 | the PS rejected a complete aggregate that covered a partial it held, so a flushed-then-retransmitted round never completed (found by Scenario J2) | fixed: superset replaces, subset is dropped |

Open limitations (not bugs): no authentication of workers (§4); one level of
aggregation (no ATP rack hierarchy); no ECN/AIMD congestion control; results
are unicast, not multicast; the
parameter server cannot separate partially overlapping aggregates (it waits
for the remaining workers' fallbacks instead of subtracting per-worker values);
Q16.16 loses gradients below ~1e-5 (see `docs/RESULTS.md` §Quantization);
wire v3's per-chunk exponent addresses that for synchronous training (§2);
the pipelined C worker uses a fixed starting exponent and only lowers it by
retrying after `OVERFLOW`; a packet carries at most 64 values
(128 verifies, 256 exceeds the verifier's instruction limit, §6); the
kernel correctness scenarios run on two namespaces (only the benchmark uses
three); nothing has run on a physical NIC or across hosts.
